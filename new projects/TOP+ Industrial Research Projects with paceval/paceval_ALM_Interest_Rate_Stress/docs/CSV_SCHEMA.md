# Canonical CSV schema and mathematical trust boundary

The input file `input/cashflows_scenarios.csv` is UTF-8 with a comma separator, dot decimal syntax and LF line endings. There are 12 columns: `scenario` (uppercase token), `cashflow_id` (`CF` followed by five digits), `side` (`ASSET` or `LIABILITY`), `t_year` (positive years, up to 40), `amount_eur_m` (positive EUR million, less than 10), `rlevel`, `rslope`, `rhump` (annual decimal zero-rate curve parameters), `tau` (positive years), `parallel`, `shortshock`, and `longshock` (annual decimal rate changes).

Exactly one finite numeric literal per numeric field is accepted; a regex rejects expressions, thousands separators, NaN/Inf, missing fields, unit suffixes and locale variants. Only after this precheck is the official `paceval_dConvertStringToFloat` invoked. Productive numeric CSV output uses `paceval_dConvertFloatToString`. Other converter paths are used for integer identifiers and JSON bookkeeping, not for productive cashflow floating-point values. Text serializations are not asserted to provide bit-exact roundtrips for every possible `double`.

Result files have explicit column headers and units: `cashflow_valuations.csv` (one row per model and scenario-cashflow), `scenario_summary.csv` (two versions times eight scenarios), `maturity_buckets.csv` (six tenor bands per version and scenario), `curve_profiles.csv` (90 maturity samples per version and scenario), `stress_surface.csv` (81 parallel/short-shock pairs under V2), `model_comparison.csv`, `native_audit.csv`, `math_execution_inventory.csv`, `formula_manifest.csv`, and machine-readable JSON proof-of-execution and validation reports.
